# Design: Workspace Sample Data

## Overview

Implement [Story 2223: Load Sample Data](PRD-TENANT-DATA-ADMIN.md#story-2223-user---load-sample-data)
using curated TOML scenario definitions and runtime generation. Users load a
complete sample dataset into a workspace, then download matching OFX data to
explore the existing bank import and categorization workflow.

The original generator at `C:\Source\jcoliz\yofi\YoFi.SampleGen` is a reference
for financial patterns, not a component to copy unchanged. Preserve its realistic
recurrence, merchant alternatives, and amount/date variability, without retaining
its dependency on periodically regenerated, dated files.

This document designs sample data and its entry into Data Administration. It
does not implement or fully design Stories 2220-2222 and 2224.

## Decisions

| Area | Decision |
|------|----------|
| Generation | Generate records in the running app from bundled, curated definitions |
| Definitions | TOML, not XLSX and not application configuration |
| Location | Application service for generation; Application feature for orchestration |
| Authorization | Workspace Owner required for the entire Data Administration page and its sample endpoints |
| Initial catalog | One Personal Finance scenario; retain a scenario selector for later additions |
| Loading | Load the whole scenario at once; no entity-type selection |
| Existing data | Preserve it; allow repeated loading with a warning that duplicates will be added |
| Current entities | Transactions and payee matching rules |
| Paychecks | One net-pay transaction per paycheck, not a breakdown of deductions |
| Budgets | Deferred |
| Navigation | Manage Data action on workspace cards; workspace selector on destination page |
| Route identity | Workspace key in the URL, synchronized with the current-workspace preference |
| XLSX | ClosedXML preferred for the separate general import/export work; not needed by sample generation |
| Offline tooling | Optional future consumer of the same generator, not a production refresh dependency |

## Scope and Current Model

The initial scenario provides realistic income, housing, utilities, food,
transportation, healthcare, personal spending, and entertainment patterns.
Payee matching rules cover the payees generated by those patterns.

There are no separate category or payee entities to create for this feature.
Categories are strings on the current transaction category representation and
payee matching rules.

Although user-facing multi-split functionality is deferred, the current
[Transaction](../../../src/Entities/Models/Transaction.cs) already contains splits.
[TransactionsFeature](../../../src/Application/Features/TransactionsFeature.cs)
creates an internal Order=0 split for a transaction's amount and category.
Sample loading must preserve this behavior. "No splits" in the initial scope
means no user-visible, multi-component transactions, not bypassing this invariant.

The V1 paycheck group must become net income after employee deductions.
Do not treat gross salary as spendable income or emit separate deduction
transactions that subtract those amounts again. Employer retirement matching and
its offset are not checking-account cash movements. Preserve the source
definition as migration reference rather than enabling unsupported group fields.

Loan payments may be represented as ordinary cash-outflow patterns initially.
Loan amortization, principal/interest breakdown, and loan-specific matching-rule
behavior are not part of this implementation.

## User Experience

### Entry and workspace identity

Add an Owner-only **Manage Data** action to each workspace card on
[workspaces.vue](../../../src/FrontEnd.Nuxt/app/pages/workspaces.vue).
It navigates to the proposed route:

`/workspaces/{workspaceKey}/data-administration`

The corresponding Nuxt page is proposed as
`app/pages/workspaces/[workspaceKey]/data-administration.vue`. Verify coexistence
with the existing workspaces page during implementation.

The clicked card determines the workspace even when a different workspace was
previously selected. Validate membership before synchronizing the shared
current-workspace preference. Do not silently substitute another workspace when
the route key is invalid, unavailable, or unauthorized.

Reuse [WorkspaceSelector](../../../src/FrontEnd.Nuxt/app/components/workspace/Selector.vue),
extending it only as necessary to coordinate route changes and block selection
before its global-store mutation when an operation is pending.
Changing this selector also changes the application-wide workspace, as it does
elsewhere. The URL is authoritative for operations on this page; browser
Back/Forward must synchronize the selector and page context.

Display **Data Administration - {workspace name}** prominently. Editors and
Viewers cannot use the page. If the shared selector selects a workspace where
the user is not Owner, show an access-denied state with the selector still
available; do not retain actions or results from the previous workspace.

### Sample data section

Show:

1. Scenario selector, initially containing **Personal Finance**, and description.
2. Inclusive start/end dates for historical sample transactions.
3. Preview counts for Transactions and Payee Matching Rules.
4. **Load Sample Data** action for the entire dataset.
5. Separate OFX start/end dates and **Download Sample OFX** action.

There are no per-type sample-loading buttons or checkboxes. Matching rules are
loaded in full even if a particular merchant has no occurrences in the chosen
historical range, so subsequent OFX transactions can be categorized.

The preview displays an exact count for the selected generation inputs, meeting
the PRD's approximate-count requirement. Internal single splits are not displayed
as a separately selectable or counted sample entity type.

Before loading, show the target workspace, dates, and counts, with this warning:

> This adds sample transactions and payee matching rules to {workspace name}.
> Existing data will not be removed or updated. Loading sample data again adds
> another copy, including additional matching rules. Existing and sample rules
> may affect categorization of future imports.

On success, show created counts by type and links to Transactions, Payee Rules,
and Bank Import. Do not imply that individual sample records can later be
removed as a batch: the PRD's Delete All Data removes real data too.

OFX download does not modify workspace data. Explain that users should load the
scenario first if they want its matching rules available. The file is then
uploaded through the existing Bank Import page and normal review workflow.

### Switching and asynchronous operations

- Prompt before discarding a prepared preview or pending confirmation.
- Clear workspace-specific previews, confirmations, counts, and results on switch.
- Disable workspace switching and repeated submission during load/download.
- Guard route navigation while a write is pending; capture the workspace key
  before sending the request.
- Ignore stale responses after a route or generation-input change.
- A canceled browser request does not prove a write was canceled. On an uncertain
  outcome, show an explicit message and advise checking transactions before retrying.
  Do not automatically retry a load, since another load intentionally adds duplicates.
- Refresh role information when entering a workspace; enforce authorization on
  every server request independently of UI state.

## Dates and Defaults

Resolve defaults per request using a testable clock, never a build-time year or
global mutable year. Proposed initial convention: server UTC calendar date,
returned to the client as an explicit date. Generation itself takes dates as
inputs and never reads the clock.

For today = **2026-06-15**:

| Operation | Default start | Default end |
|-----------|---------------|-------------|
| Historical load | 2025-06-01 | 2026-03-31 |
| OFX download | 2026-04-01 | 2026-06-15 |

Historical start is the first day of the month 12 months before today's month.
Historical end is the last day of the month three months before today's month.
OFX start is the first day of the month two months before today's month.
Both ranges are inclusive and independently editable.

Validate start <= end and compatibility with current transaction date validation.
Reject excessive generation requests before allocating the full result.
The numerical limits remain an implementation decision to resolve before coding;
do not silently truncate dates or generated records.

## Application Architecture

```text
Controllers project
    SampleDataController
        Thin, tenant-scoped HTTP boundary

Application project
    Features/SampleDataFeature
        Catalog, defaults, preview, loading, OFX coordination
    Services/SampleDataGenerator
        Definitions + range + seed -> generated records
    Services/SampleScenarioLoader
        Bundled TOML -> typed, validated scenario catalog
    Helpers/SampleOfxWriter
        Generated transactions -> OFX stream
    SampleData/Scenarios/personal-finance.toml
        Curated scenario asset
```

These are proposed names, not existing implementations. Keep the classes small;
do not introduce a separate project, plugin framework, or generic generation
platform. Interfaces are useful where substitution is needed, not mandatory
for every class.

### SampleDataGenerator

Accept a validated scenario, explicit range, and scenario seed. Return an
in-memory dataset containing transaction inputs and matching-rule inputs.
No tenant context, database operations, HTTP dependencies, TOML parsing, or OFX
serialization belong in the algorithm.

Use the same generator for preview, load, and OFX. OFX omits categories; loaded
transactions have the expected category directly.

### SampleDataFeature

Orchestrate the use cases, resolve defaults, validate requests and generated DTOs,
and delegate persistence to shared Application import/create behavior.
Attach the current authorized tenant only at the persistence boundary.

Reuse the common key-based import semantics specified by the tenant-data PRD:
sample inputs contain no entity Keys, so every record takes the create branch.
Never serialize to XLSX and read it back just to reach that path.

The general import feature is not currently present in this checkout. If sample
loading is implemented first, establish a small shared, typed persistence
operation that the future file importer can call. Preserve category sanitization,
default-split construction, and rule initialization from existing features;
extract shared construction logic where necessary rather than maintaining a
second set of business rules.

### Dependency registration and assets

Features are already registered as scoped services by
[AddApplicationFeatures](../../../src/Application/ServiceCollectionExtensions.cs).
Register the loader/generator explicitly with lifetimes consistent with their
state. Shared definitions must be immutable; generation state is per invocation.

Proposed packaging: embedded TOML resources in Application, loaded and validated
at startup. This avoids dependence on working directories, host-specific asset
copying, or public `wwwroot/sample-data` files. Fail startup with actionable
diagnostics if a bundled scenario is invalid; do not expose a broken catalog.

## TOML Contract

Add a direct TOML parser dependency to Application and its version to
[Directory.Packages.props](../../../Directory.Packages.props).
Do not use `Alexinea.Extensions.Configuration.Toml` or the application
configuration provider to load scenario documents.

Tomlyn is a candidate, not a finalized dependency. Verify typed mapping,
diagnostics, supported runtime, license, unknown-member handling, and numeric
conversion before choosing a supported stable version.

Illustrative initial schema:

```toml
id = "personal-finance"
revision = 1
name = "Personal Finance"
description = "Realistic household income and spending."
seed = 42

[[patterns]]
id = "coffee"
category = "Food:Away:Coffee"
payees = ["Starbucks", "Uptown Espresso", "Tim Hortons"]
annual_amount = "-1170.00"
frequency = "weekly"
repeats = 3
amount_jitter = "high"
date_jitter = "high"

[[patterns]]
id = "net-paycheck"
category = "Income:Salary"
payees = ["Megacorp Inc"]
annual_amount = "61678.00"
frequency = "semi-monthly"
repeats = 1
amount_jitter = "none"
date_jitter = "none"
```

The paycheck number is illustrative and must be reconciled against the original
definition before shipping. Quoted annual amounts are intentional: parse them
directly as invariant-culture `decimal`, avoiding a binary floating-point
intermediate. Use decimal arithmetic for financial amounts throughout.

Validate:

- Unique stable scenario and pattern IDs, positive revision, and required metadata.
- Nonempty merchant arrays, valid categories, and existing DTO length constraints.
- Nonzero annual amounts, positive repeats, recognized frequencies/jitter levels.
- No unknown or unsupported fields, including V1 group, loan, or budget constructs.
- No conflicting merchant/category definitions within one scenario.
- Supported recurrence/jitter combinations.
- Generated DTO validity, including no zero-valued transactions after rounding.

Report scenario, pattern, field, and source position where available. Do not
silently drop malformed patterns or substitute defaults for unknown values.
No user-provided TOML uploads or arbitrary scenario file paths are supported.

## Generation Semantics

### Recurrence and variability

Preserve the V1 model of annual target amounts distributed over recurrence:
52 weekly periods, 24 semi-monthly periods, 12 monthly periods, four quarterly
periods, or one yearly period, multiplied by repeats.

For the first implementation, anchor periods to each calendar year, not to the
request start. Weekly periods start January 1 at seven-day intervals, matching
the original 52-period model. Semi-monthly dates are the 1st and 15th.
Other periods begin at their calendar boundaries.

Generate occurrences in their canonical periods, apply deterministic jitter,
and only then filter by the inclusive requested range. Date jitter must stay
within that period and calendar year; handle actual month lengths and leap years.
Do not scale the annual target to the request length or force a partial range
to contain a full year's spending.

Start with the original amount jitter proportions: none=0%, low=10%,
moderate=40%, high=90%. Round transaction amounts to two decimal places using
an explicitly documented rounding rule. Annual amounts are targets; jitter and
rounding mean realized totals need not equal them exactly.

### Determinism and identifiers

Generation must be stable across overlapping ranges and independent of pattern
ordering, request concurrency, or unrelated patterns. A single mutable random
sequence seeded once per request is insufficient.

Derive per-occurrence randomness from stable inputs: scenario ID/revision, seed,
pattern ID, calendar year, period index, repeat index, and the random purpose
(date, amount, or payee). Use a specified stable algorithm, not a process-randomized
runtime hash. Persist no shared mutable year or random generator.

Derive a stable synthetic ExternalId/FITID from the same occurrence identity.
Include a sample namespace and stay within the existing 100-character limit.
Direct load and OFX must use the same identity for the same occurrence.
Overlapping OFX downloads therefore exercise existing duplicate detection.

Stable ExternalIds do not make direct sample loads idempotent: Keys are new on
every load, and duplicate sample ExternalIds may intentionally exist after
repeated loading. Explain this distinction in tests and UI messaging.

Use a fixed scenario seed in the initial release; do not expose a randomization
control. Carry scenario revision with preview/load/download inputs and reject
stale revisions after deployment, asking the user to refresh the preview.
Revision is internal scenario identity, not XLSX schema versioning.

### Matching rules

Generate one substring rule per distinct merchant/category pair using the current
rule DTO. Deduplicate within the generated dataset only. Do not update or remove
existing workspace rules. Let the existing persistence path assign Keys and
initialize audit and usage fields.

Test every generated merchant against the actual matching implementation in an
otherwise empty workspace. Avoid overlapping patterns that select an unintended
category. In a populated workspace, normal rule precedence still applies;
the feature cannot promise that existing rules will never interact with samples.

## Loading and Persistence

1. Validate scenario/revision and request dates.
2. Regenerate the deterministic dataset and calculate counts.
3. Validate all generated transaction and matching-rule DTOs explicitly.
   Controller validation alone does not validate internally generated records.
4. Apply the whole dataset in one database transaction through the shared
   create/import path.
5. Return committed created counts; updated counts are always zero.

Proposed sample-specific guarantee: all-or-nothing across both types. This is
stronger than the general file import's per-worksheet behavior and avoids rules
without their historical data, or historical data without its rules.
Coordinate through one unit of work; do not call independently committing
per-item feature methods and claim the operation is atomic.

Do not clear existing transactions, rules, or pending bank-import reviews.
No new tables, migrations, sample-load history, or sample-only deletion mechanism
are required initially.

## OFX Output

Generate an OFX bank statement for one synthetic checking account using the same
scenario, seed, revision, recurrence, merchant text, amounts, and occurrence IDs.
Use synthetic institution/account metadata only.

Keep the writer separate from the generator. Inspect existing library writing
capabilities before deciding whether a small dedicated writer is required; the
presence of an OFX reader does not establish a supported writer API.

Requirements:

- Importable by the existing [OfxParsingHelper](../../../src/Application/Helpers/OfxParsingHelper.cs).
- Valid statement date range and deterministic transaction FITIDs.
- Correct escaping, invariant amount/date formatting, and preserved amount signs.
- Complete merchant text so scenario rules match after parsing.
- Consistent account/source metadata between direct-loaded and OFX records.
- Statement balance metadata consistent with the chosen synthetic opening balance;
  document that convention and do not imply real bank balances.
- No category assignment encoded as a substitute for testing matching rules.
- Filename identifies scenario and requested dates.

Validate signs end-to-end: the existing parser preserves OFX amount signs.
Use bank-style negative spending and positive income; do not infer a conversion
from potentially ambiguous model comments.

## Proposed API

Use a dedicated thin `SampleDataController` under:

`/api/tenant/{tenantKey:guid}/admin/sample-data`

All endpoints require the existing tenant Owner authorization policy and tenant
middleware. The scenario catalog is exposed through this same authorized boundary.

| Method | Suffix | Purpose |
|--------|--------|---------|
| GET | `/scenarios` | Catalog, supported entity types, revisions, and resolved default ranges |
| POST | `/preview` | Exact counts for scenario/revision and historical date range |
| POST | `/load` | Create the complete dataset for the selected range |
| GET | `/ofx` | Download OFX for scenario/revision and requested OFX range |

Use generated API client contracts and explicit request/response DTOs. Preview
returns the resolved inputs plus per-type and total counts; load returns the
resolved inputs and committed per-type created counts. Do not expose entity IDs
or accept a caller-supplied tenant ID in dataset payloads.

Return standard ProblemDetails for invalid requests, unavailable scenarios,
stale revisions, and failures. Follow repository status/exception conventions.
Do not return success-shaped results for failed loads. A file response returns
the appropriate OFX content type and attachment filename.

Log actor/workspace, scenario/revision, date range, operation, counts, and
success/failure using existing controller logging conventions. Do not log full
generated financial records.

## Testing and Acceptance

### Unit

- TOML binding, quoted decimal precision, unknown-field rejection, and diagnostics.
- Catalog uniqueness and semantic validation for every bundled scenario.
- June example defaults, January rollover, leap years, and inclusive range edges.
- Recurrence counts and repeats; annual amounts are not multiplied accidentally.
- Jitter bounds, sign preservation, rounding, and no zero-valued output.
- Overlapping-range equality, pattern-reorder stability, and parallel generation.
- Stable IDs across preview/load/OFX for the same scenario revision.
- Net-pay migration arithmetic and absence of separate paycheck deductions.
- Matching-rule coverage of all merchant alternatives.

### Application/data integration

- Whole-set creation with fresh Keys and correct tenant assignment.
- Existing records unchanged; repeated load adds another complete copy.
- Internal single splits and category sanitization preserved.
- Matching-rule audit/usage initialization and invalid generated DTO rejection.
- Rollback both types on a persistence failure.
- No effects on another tenant or pending bank-import reviews.

### Controller and functional

- Owner succeeds; Editor, Viewer, nonmember, and unauthenticated access fail.
- Card B opens workspace B even when A was previously current.
- Selector, refresh, and Back/Forward keep route/store/operation targets aligned.
- Unauthorized workspace selection and invalid keys do not fall back silently.
- Switching clears state; pending writes cannot be retargeted.
- Full-set preview, duplicate warning, confirmation, and created counts.
- OFX parses with matching dates, amounts, merchants, and IDs.
- OFX import applies expected scenario rules in a clean workspace.
- Importing overlapping OFX ranges detects existing occurrences.
- Empty historical ranges, stale previews, API errors, and uncertain write outcomes
  produce explicit feedback.

Measure representative default and maximum-size scenarios for latency, memory,
and concurrent requests. Set generation limits from those results before release.

## Delivery Sequence

1. Reconcile the original Personal Finance definitions and net paycheck.
2. Select/verify a direct TOML parser; implement typed schema and validation.
3. Implement deterministic generation and its focused tests.
4. Establish/reuse shared persistence with all-or-nothing sample loading.
5. Implement OFX output and round-trip tests through the current bank importer.
6. Add Owner-only endpoints and generated client contracts.
7. Add card entry, route/selector synchronization, and sample section.
8. Validate authorization, workspace transitions, repeats, and resource limits.

No sample-related XLSX dependency is required for these steps.

## Future Work

### Multi-split transactions

Restore paycheck groups with gross income, taxes, insurance, retirement
contributions, and other deductions when supported by the user-facing app.
Add other grouped transactions and loan principal/interest breakdowns as needed.
Ensure splits reconcile to the net bank transaction.

This requires coordinated changes to the TOML schema, generator output,
validation, shared persistence, preview/count presentation, and tests. Do not
implement dormant grouping or amortization infrastructure in this story.

### Budgets

Generate budgets from the same scenario patterns once V3 budgeting semantics
are defined. Determine how annual targets, partial-year ranges, jitter, and loan
components translate into budgets then. Do not assume the V1 budget model maps
directly to V3.

### Additional scenarios and offline tooling

Add curated scenarios as product needs become clear. Each must include coherent
transaction patterns and matching rules with end-to-end coverage. A CLI may
reuse the generator for fixtures, screenshots, and debugging, but production
must never depend on someone rerunning it to refresh calendar dates.

### Other administration capabilities

The page can acquire general XLSX import/export and Delete All Data through
their own story designs. ClosedXML is the preferred XLSX choice discussed so
far; isolate it at file-processing boundaries and explicitly avoid formula
evaluation. It is unrelated to TOML scenario loading.

## Open Implementation Decisions

- Final TOML parser/version after the compatibility and diagnostics evaluation.
- Maximum allowed date span and generated record count, with explicit rejection
  and UI guidance rather than truncation.
- Exact recurrence date-window mapping for low/moderate/high date jitter and
  rounding rule, pinned by tests before scenario migration is accepted.
- Confirm server-UTC defaults are appropriate until a user timezone preference
  exists; display the resolved dates so they are never implicit.
- Final synthetic account metadata and OFX statement balance convention.

These items do not change the agreed architecture or user-facing scope.
